# 整库容量扩展方案：单场继续设限

2026-10-21 用户已确认方向：**先支持整库超过 64MiB，单场正文继续设限**。本文件是实现方案；本轮代码、安装包和原有 64MiB 检查均未改变。首个产品整库上限尚未选定，须由公开压力数据确定，不宣称无限容量。

## 先决状态

差量确认已完成本轮原生验收：iOS 86 核心、3 冷启动、7 系统 UI、3020 公开批量结果通过；Android 16 项 S9 原生通过。Android 6000 场无正文追加复用已校验的插入语句，原生事务中位 878.631ms；这些结果不等于扩大容量已实现，也不是生产界面确认的完整计时。

## 代码证据与必须拆开的限制

| 范围 | 现状及相关实现 | 扩展方案 |
| --- | --- | --- |
| 整库容量 | Android `IndexedSnapshot.checkSize` 使用 `PdfSpool.MAX_BYTES`；iOS `LogbookStore.transaction` 汇总 state/record 元数据和正文后与 `logbookMaximumBytes` 比较 | 独立的整库逻辑字节预算，仍在最终 CAS 事务中核对全部旧数据和变化数据 |
| 单场及单次来源 | 网络解压、按场暂存、部分单实体请求仍有 64MiB 保护 | 首轮不扩大单场能力；单场按完整序列化后的 UTF-8 逻辑字节计量，不能把 raw/manual 两个字段各自放大到 64MiB。最终口径须与当前计量回归对齐 |
| 原生传输/只读租约 | `SnapshotUpload`、`ReadLease` 复用 PDF spool 上限；桥接片段仍为 256KiB | 大库总量和小片段大小分离；可信原生按操作用途选择预算，不能让客户端任意指定上限 |
| Worker 完整候选 | `snapshot-job.ts` 的 prepare 仍整份 stringify、UTF-8 编码、previewBackup、再次编码 | 大库备份/恢复不能继续把全部正文读入 JS。复用版本化租约，按有界片段处理；元数据、关联和所有业务字段仍完整校验 |
| 本地来源读取 | `local-source.ts` 调用 `response.arrayBuffer()` 后计算整体摘要，且拒绝超过 64MiB | 对大库备份/恢复提供流式读取/摘要实现；旧小文件路径保留，不能只提高这里的数字 |
| JSON/ZIP 备份与恢复 | `backup.ts` 的 JSON 输入/ZIP 文件为 64MiB，ZIP 解压合计另有 128MiB；当前 `unzipSync`、`zipSync` 和完整 entries/backup.json 占内存 | 完整备份和完整恢复一同改为有界流，明确压缩、解压合计、条目数、附件及单场预算；重复/危险路径、摘要、缺项和 ZIP 膨胀保护全部保留 |
| TXT/PDF/独立附件 | 另有输出文件和附件规则 | 本阶段不把整库容量直接套用到每个文件。现有单文件限制继续明确拒绝，不能截断或悄悄漏导 |

“逻辑字节”继续表示业务快照的完整 UTF-8 数据量，不是 SQLite 文件大小、压缩后大小或 JS 字符数。当前 Android/iOS 容量实现的细节不同，分别对照现有等价夹具验证；容量扩展不得借机覆盖 Android v4 正文块或 iOS v1 body 列。

## 深模块与接缝

把大库备份/恢复的复杂性放到现有原生存储及版本化文件租约之后，界面继续只需要少量接口事实。Android 和 iOS 是两个真实适配器，分别保留自己的 SQLite、授权、文件提供器和发布实现；不新增让调用方自行拼接、校验和多次保存正文的浅层转发模块。

建议的大库恢复接口语义如下，名称为设计草案，不是本轮已实现接口：

1. **预览**：消费已选择来源的有界流，返回绑定 revision 的租约、完整数量/字节摘要及明确警告。解析器逐项严格校验所有实体、未知/重复字段、顺序、来源、正文与全部关联；正文留在私有暂存，不把整库正文返回界面。校验结论不能由客户端布尔值代替。
2. **确认**：只接收该租约和预览 revision。复查原目录及即时授权，核对完整长度/摘要与最终图，在一个 CAS 事务中发布全部记录或完全回滚。超时/回复丢失不得换接口或换 revision 自动重放。
3. **取消/释放**：仅清理本次确切租约的私有暂存，幂等处理；不清理生产库、已登记归档或其他任务文件。进程重开只按已有证明恢复/清理，不扫描猜测用户文件。

完整备份继续从一个确定 revision 生成不可变流式输出，回读长度/摘要成功后才登记。沿用原自动备份周期、十份轮换、修改判断、授权及新文件规则；不恢复操作前安全副本。备份完成回调不能覆盖期间产生的新业务 revision。读取一致性和存储队列占用要分别测量，不承诺长读天然不影响写入。

## 实施顺序与验收门槛

1. **先拆预算，不开启新上限。** 把整库、单场、传输片段、归档文件和解压合计的用途分开，默认值保持现状。Android 快照传输不再被 PDF 的全局常量暗中控制；iOS 同样区分用途。使用原公开夹具证明小库成功/失败语义、容量计量和旧接口完全一致。
2. **先完成大库完整备份和恢复。** 流式 JSON/ZIP、同 revision、完整回读与最终 CAS 一起实现。保留现有 schemaVersion 2 的业务结构；仅采用流式处理并不要求改变业务字段。若确实需要新的容器或分卷格式，另行定义版本和兼容规则，不能默默让旧格式缺正文。大库备份在旧版会遇到旧上限，不能承诺旧版可读写；回退前须保护数据库、偏好、登记和归档。
3. **再接入普通保存与批量。** 新库上限必须同样覆盖新增、手动编辑、表格差量、网络暂存、恢复、自动备份及进程重开。单次小差量可继续保持小请求上限；超过接口上限的单次操作整体拒绝或改用已验租约，不拆成多次隐式提交。能力缺失时明确拒绝大库操作，不能退回会整库分配的旧路径。
4. **最后启用一个有限的整库目标。** 用相同公开数据在 S9 普通堆和 iOS 独立适配器上做规模阶梯，至少包含超过现有上限的样本，例如 96MiB、192MiB；这些是验收样本，不是已决定的产品上限。分别扩大正文量和实体数量，测量 UI、Worker、桥接、原生阶段、峰值内存和私有暂存空间，再确定可支持的目标及余量。

必须覆盖：旧库保留升级、全部旧正文/原始块及元数据、末场/顺序/完整回导、单场超限、整库超限、异常大字段、并发网络的总在途字节、ZIP 膨胀/危险路径/缺失附件、磁盘不足、目录/授权变化、旧 revision、中途 SQL/I/O/摘要失败、取消、进程中断、备份与编辑交错、重开后的完整备份恢复。大库只恢复成功一部分、备份遗漏正文、提前显示成功、扩大普通堆或清空生产应用均不能作为通过方式。

## 当前确认与尚待决定

- 已确认：整库先扩，单场继续设限；保留完整关联、授权、CAS、事务回滚、自动备份和平台差异。
- 当前执行状态：**仅完成方案，64MiB 未放开，没有新容量安装包。**
- 尚待后续实测决定：首个有限整库上限、各操作的可信字节预算、附件/归档组合预算及设备内存/磁盘余量。不得以只改一个常量替代上述实现与验收。
