## 第一阶段实现（`a5a987c`，后续变化见第二阶段）

- 文字格式在独立 `export-worker.js` 生成，文件缓冲以 transferable 返回；正文读取/校验线程不加载 DOCX 编译器，也不被 ZIP 生成占用。
- DOC / DOCX 不再先拼接一份不用的纯文本；DOCX 使用原依赖生成的五种普通/空段落与完整包模板，批量填入转义后的全文并压缩，不为每条发言创建/编译通用对象树。
- 同一实际数据的 Node 对照：合成 DOCX 约 4.035s→0.184s，单场约 0.123s→0.052s。全部 Word 正文 XML 相同；除正常生成时间外，其他 ZIP 部件均相同。文件压缩字节不要求一致；不能把 Node 数字当成 S9。
- 超过 8 MiB 的文字文件与 PDF 共用有界私有暂存，256 KiB 顺序传输，由新的文字完成接口按白名单 MIME 流式新建/回读/登记；仍是 64 MiB/文件，失败仅清理本次文件。较小文件使用 FileReader 异步编码后一次写入，阈值及最终速度待真机复测。原 `writeArchive` 供既有备份/表格等调用，不改变数据保存规则。
- 独立 SQLite 归档索引做过试验：845 条旧登记迁移和重开逐项相同，业务数据、版本和目录不变；但本轮逐场总耗时没有改善，因此**未纳入源码**。发布代码仍使用原归档登记结构，仅把列表读取移到存储队列，避免目录查询占用 UI。试验应用内的索引和最终快照必须一起留仓库外，不能把其新登记反向冒充旧结构可识别。
